# Task: full code review of Into The Fray, with every fix applied

Into The Fray is an online card table for Marvel Champions, played in the
browser, solo or multiplayer, as a pure sandbox (no rules automation): a
stateless Go backend with Redis, a Svelte 5 + Vite SPA, and card data
generated from marvelcdb and Cerebro.

Two modes, set by whoever launched you:

- **Delegated**, when the `cat >` command under "Final signal" targets a
  real file under `/tmp`: you run in a dedicated Casper workspace, a Git
  worktree of `intothefray` on your own branch created from `{{BASE}}`, with
  its own ports in `.env.casper`. Work autonomously: nobody watches this
  session in real time. Do NOT merge into `main`, do NOT push, and do NOT
  delete the workspace: the user reviews and merges.
- **Foreground**, when that command still shows a placeholder in double
  braces: you run in the user's own checkout, on its current branch, while
  the user follows along. Commit there; never push. Record
  `git rev-parse HEAD` at the Baseline step: that commit stands for
  `{{BASE}}` wherever it appears below.

Either way, launching this review is the go-ahead to commit the review's
work on this branch, nothing more (no push, no tag, no deployment: a push
to `main` publishes the image and deploys Pages and the backend).

## Scope

The whole repository: `cmd/` (`intothefray`, `packgen`), `internal/`

`version`) and their tests and `testdata/`, `packs/` (`curated/`, the
`embed` package in `packs.go`), `web/` (`src/` with `screens/`, `lib/`,
`components/`, `table/`, `styles/`, `App.svelte`, `main.ts`,
`test-setup.ts`; `public/`, `scripts/`, `index.html`, the Vite, Svelte,
TypeScript, ESLint and Prettier configs, `Caddyfile`), `Makefile`,
`Dockerfile`, `.dockerignore`, `.gitignore`, `compose.yaml`, `.air.toml`,
`.golangci.yml`, `mise.toml`, `.casper.json`, `scripts/casper.sh`,
`.github/workflows/`, `README.md`, `CLAUDE.md` and
`.claude/project-memory/`.

Leave unchanged:

- `.claude/skills/full-review/` (this skill).
- `packs/dist/`: generated by `make packs`, never edited by hand. Do not
  run `make packs` either: it fetches marvelcdb and Cerebro over the
  network and rewrites every pack. A `packgen` refactor keeps its output
  byte-identical (proved by the `internal/packgen` tests); a change that
  should alter `packs/dist/` goes in the final report.
- `go.mod`, `go.sum`, `web/package.json` versions, `web/pnpm-lock.yaml`,
  the tool pins (`mise.toml`, the golangci-lint `version:` in `ci.yml`, the
  images in `Dockerfile` and `compose.yaml`, the action versions in
  `ci.yml`): no dependency bump, no new dependency. Removing a dependency
  nothing uses is allowed (`go mod tidy`, `pnpm remove`). Report an
  outdated pin; do not change it.
- The local, gitignored directories: `docs/`, `.superpowers/`,
  `.superlite/`, `tmp/`, `.env.casper`. Never commit any of them.

## Design docs (local only)

The design specs, plans and rulings live in `docs/superpowers/` (`specs/`,
`plans/`, `rulings/`, `STATUS.md`). That directory is gitignored and exists
only in the main checkout, never in a worktree. Find it from any checkout:

```bash
main_checkout="$(dirname "$(git rev-parse --path-format=absolute \
  --git-common-dir)")"
ls "$main_checkout/docs/superpowers"
```

Read them there; never copy them into this checkout and never commit them.
They are dated design records, not living docs: do not edit them. When a
spec and the code disagree, the memory notes and `git log` say which side
is intended (see rule 2); a spec left stale by a deliberate change goes in
the final report as a question for the user.

## Visual checks

The UI is a web app, so it can be checked in a real browser. In the
delegated mode, use the Casper browser panel (read the `casper` skill and
its `references/browser.md` and `references/terminal.md` first):

1. Docker must be running (`docker info`) and `air` installed
   (`command -v air`): `make dev` starts Redis and Caddy in containers and
   runs the server under Air. If either is missing, skip the browser checks
   and turn each one into a manual check.
2. Start the hot-reload stack in a Casper terminal, so that it uses this
   workspace's ports, and keep the terminal id it prints:

   ```bash
   casper terminal new --command "scripts/casper.sh dev"
   ```

3. The web app is at `http://localhost:$WEB_PORT`, with `WEB_PORT` from
   `.env.casper` (8080 without it). `make dev` rebuilds `web/dist` on every
   change (`pnpm watch`) and Air restarts the server, so reload the page
   (`casper browser reload --wait`) after a change.
4. For each change that shows on screen, check the screens it touches
   before and after the change: `casper browser console --clear`, then
   `load`, `wait`, `console --level warn` (no warning or error),
   `screenshot` (read the PNG back and compare). Use off-screen captures
   (`--width`, `--height`) for the
   compact layouts (600 px wide, 500 px tall; see the
   `project_top_bar_auto_hide` note). Drive the flows with `click`, `type`
   and `key`: create a game from Home, the lobby, the table.
5. When the checks are done, close the terminal
   (`casper terminal close <id>`) and stop the containers with this
   workspace's environment:

   ```bash
   (set -a; . ./.env.casper; set +a; make infra-down)
   ```

In the foreground mode, there is no browser panel: list the checks for the
user instead.

Whatever the panel cannot prove becomes a **manual check** in the final
report: what changed, and the exact steps to see it with `make dev`.
That covers at least multiplayer flows (two browsers on one game: presence,
fan-out, spectators), the feel of drag and drop and of the card animations,
fullscreen and Escape handling, and touch input.

## Rules

1. **Simplify the code as much as possible and delete dead code**: unused
   Go types, functions, parameters, fields, constants, files and branches;
   unused Svelte components, props, state, CSS, TypeScript exports and
   test helpers (`*.testing.ts` files included); `Makefile` targets,
   variables and scripts nobody uses; compose, Docker, Caddy and CI settings
   that restate a default; stale, duplicated or contradicting passages in
   `README.md` and `CLAUDE.md`; stale, duplicated or contradicting memory
   notes and their `MEMORY.md` lines. Two traps: a Go function only the
   tests reach is not dead when it is a test seam the design relies on, and
   an export only a test imports is dead only if the test exists for it
   alone.
2. **Be rigorous about the accuracy of every document against the code.**
   Check every claim in `README.md`, `CLAUDE.md` (its module list and
   commands included), the memory notes, the code comments, the `make help`
   texts and `scripts/casper.sh` against what the code does. The memory
   notes record the decisions: when a note and the code disagree, find out
   which side is intended (the note, the local design spec, `git log`). A
   deliberate as-built behaviour means fixing the note; a departure from a
   recorded decision means fixing the code. When neither source settles it,
   do not guess: leave both as they are and list the question in the final
   report. Claims about external tools and libraries go against a primary
   source: context7 or the official documentation for Go, Svelte 5, Vite,
   Vitest, go-redis, Redis, Caddy, Docker Compose, GitHub Actions and
   GitHub Pages; the marvelcdb, mc4db and Cerebro data for card facts
   (see the `reference_card_sources` note).
3. **Remove duplicated code**: helpers, components, actions, parsing and
   test fixtures that two or more places repeat, merged into the package or
   module that owns them, with one name and one behaviour. Look across Go
   packages (`internal/game`, `server`, `store`, `pack`, `packgen`), across
   web folders (`table/`, `screens/`, `components/`, `lib/`), and between Go
   and TypeScript: the WebSocket messages of `internal/server/protocol.go`
   mirrored in `web/src/lib/session.svelte.ts`, the game types of
   `internal/game/` (`game.go`, `state.go`, `view.go`, `action.go`)
   mirrored in `web/src/lib/types.ts`, the pack schema of
   `internal/pack/types.go` read by the web app, rules and constants the
   server enforces and the client restates. Two copies
   across the language boundary stay two copies: check that they agree,
   and fix the one that drifted.
4. **Clean up remaining workarounds**: `TODO` / `FIXME` / `HACK` /
   "workaround" comments; `setTimeout`, `requestAnimationFrame` chains,
   sleeps and polling standing in for a missing signal; retries that hide a
   race; magic offsets in CSS or layout code that compensate for another
   bug; per-case exceptions; duplicated fixes. When the root cause is in
   this project's code, fix it, then delete the workaround and any memory
   note that only documents it. A workaround for a browser, Svelte, Vite,
   Redis or Caddy bug that a memory note records stays (for instance the
   Chromium Escape handling of `project_escape_in_fullscreen`): check only
   that its comment points at the note. A deliberate budget or timing (the
   presence throttle of `project_presence_budget`, the animation durations
   of `project_card_move_animations`) is a decision, not a workaround.
5. **Apply every recommendation** from the review. None is left as a
   "follow-up". If one truly cannot be applied (it would contradict a rule
   of `CLAUDE.md` or a user decision recorded in the project memory, or
   break a contract listed under "Constraints"), say why in the final
   report.

## Constraints

- `CLAUDE.md` and the project memory are the source of truth for the
  conventions: read `CLAUDE.md`, `.claude/project-memory/MEMORY.md` and
  every note it links in full before starting, and the local design spec
  of an area before reviewing it.
- **Behaviour stays identical unless a change is intended.** Every
  refactor keeps `make check` green (Go race tests, `svelte-check`, ESLint
  and Prettier, Vitest, golangci-lint) and `make build` and `make web-build`
  passing, with no new warning. Every intended behaviour change (a bug fix,
  a workaround removal) comes with a test that fails before it and passes
  after, written TDD by the code-writer.
- **The game engine stays deterministic and replayable** (see the
  `project_replayable_state` note): no randomness or state change outside
  the recorded actions. The replays under `internal/game/testdata/replays/`
  and their `*.table.golden.json` files are tests: a refactor leaves the
  replays and the goldens byte-identical. Only an intended change rewrites
  the goldens (the `-update` flag of `internal/game/random_play_test.go`),
  and the diff of every rewritten golden is checked by hand; never run its
  `-record` flag, which records the replays again from random play.
- **The views stay anti-cheat** (see the `project_constraints` note): the
  server sends each viewer only what they may see. A simplification of
  `internal/game/view.go` or of the fan-out must not leak a hand, a deck
  order, a face-down card, the seed or the resolved history.
- **Contracts stay unchanged**: the HTTP API (`GET /healthz` answering a
  plain "ok", `GET /api/version`, `POST /api/games`,
  `GET /api/games/{id}/cards`) and the WebSocket endpoint
  `GET /ws/games/{id}` with its client and server messages
  (`internal/server/protocol.go`); the pack JSON schema
  (`internal/pack/types.go`) and the curated file formats
  (`packs/curated/cards.json`, `sets.json`, `scenarios/*.json`); the Redis
  key layout (`internal/store/store.go`); the environment variables the
  server reads (`internal/config`) and the build-time ones (`VITE_API_URL`,
  `VITE_COMMIT`, `APP_INSTANCE`, the ports of `.env.casper`); the
  `healthcheck` subcommand of the container healthcheck; the SPA routes
  (`/`, `/options`, `/g/<id>`: shared game links, served by the
  `try_files` fallback of `web/Caddyfile` and the `404.html` copy of
  `ci.yml`); the browser storage keys (`itf-*`); the release contract
  with `intothefray-infra` (the GHCR image name and tags, the
  `deploy-app` dispatch and its `client_payload.sha`, see the
  `project_deployment` note). The frontend on Pages and the backend on the
  VPS deploy separately and can run different commits, so a wire-format
  change breaks live games. A contract bug goes in the final report, not
  into a silent fix.
- **No compatibility for games in progress** (see the
  `feedback_no_live_game_compat` note): a change to an action's internal
  representation takes the simplest design, with no compatibility fields
  or migration for histories stored in Redis.
- **Casper stays optional** (see the `project_casper_optional` note): the
  build files never call or mention Casper; its wiring stays in
  `.casper.json` and `scripts/casper.sh`.
- Memory notes are timeless (see the `feedback_timeless_memory` note and
  the wording rules at the top of `MEMORY.md`): no dates, no narration of
  what changed.
- All project text in English: code, comments, docs, UI copy, commit
  messages (a verb + action subject). Line length: Markdown 80 columns,
  code 120.
- Follow `CLAUDE.md`: delegate every code change to the
  **skillbox:code-writer** agent (one code-writer per task, a commit per
  task); persist and prune memory with the **skillbox:project-memory**
  skill, never the built-in auto-memory.

## Process

1. **Toolchain**: in the delegated mode, first wait for the workspace's
   `setup` script, which runs alongside you: `.env.casper` and
   `web/node_modules/.modules.yaml` must exist before you install or run
   anything. `go version` must satisfy `go.mod`; `node --version` and
   `pnpm --version` must match `mise.toml`; `golangci-lint version` must
   match the `version:` of the lint step in `.github/workflows/ci.yml`. If
   one fails and cannot be fixed without the user, that is a blocker: see
   "Final signal". Run `make web-install` if `web/node_modules/` is
   missing.
2. **Baseline** on the base commit, before touching code: `make check`,
   `make build` and `make web-build` (keep their warnings and any failure:
   one that also fails here is pre-existing, not yours). Count the tests,
   Go (subtests included) then Vitest (its `Tests  N passed` line):

   ```bash
   go test -race -shuffle=on -json ./... | grep -c '"Action":"pass".*"Test":'
   (cd web && pnpm test) | grep 'Tests '
   ```

3. **Review** with **skillbox:code-reviewer** agents in parallel, each
   given the rules and constraints above and the local design specs of its
   area: one for the game engine (`internal/game`, its replays and
   goldens); one for the server side (`internal/server`, `internal/store`,
   `internal/config`, `internal/decks`, `internal/version`,
   `cmd/intothefray`), with the protocol and the anti-cheat views; one for
   the card data (`internal/pack`, `internal/packgen`, `cmd/packgen`,
   `packs/curated`, `packs/packs.go`); one for the web table
   (`web/src/table/`, the largest area, split in two after listing its
   files if needed, for instance rendering and animations versus
   interactions, boxes and presence); one for the rest of the web app
   (`screens/`, `lib/`, `components/`, `styles/`, `App.svelte`,
   `main.ts`, `test-setup.ts`, `web/public/`, `web/scripts/`, the web
   configs); one for the build and delivery tooling (`Makefile`,
   `Dockerfile`, `.dockerignore`, `.gitignore`, `compose.yaml`,
   `web/Caddyfile`, `.air.toml`, `.golangci.yml`,
   `mise.toml`, `.casper.json`, `scripts/casper.sh`,
   `.github/workflows/ci.yml`); one for duplication across modules and
   between Go and TypeScript; one for the docs and the memory.
4. **Apply**: merge the findings into one list, then apply all of them, in
   small logical commits on this branch.
5. **Verify**: `make check`, `make build` and `make web-build` with no
   warning beyond the baseline, at least the baseline's test counts and no
   new failure, the replay goldens unchanged unless a change intended
   otherwise, then the browser checks of "Visual checks". When a build file
   changed, also run the checks only CI runs, with Docker running:
   `go vet ./...`, `docker build .`, `docker compose config --quiet` and
   the Caddyfile validation step of `ci.yml`. A change to `ci.yml` itself
   becomes a manual check (it runs on the next push). Re-read the docs and
   notes touched by a behaviour change against the code.
6. **Final pass**: a last **skillbox:code-reviewer** pass on the whole
   branch diff (`git diff {{BASE}}...HEAD`), then apply what it finds and
   verify again.

## Final signal

The report, in both modes: findings per rule and how each was fixed; doc
and memory corrections with their source; lines of code removed
(`git diff --shortstat {{BASE}}...HEAD`); Go and Vitest test counts before
and after; user-visible changes; what was checked in the browser panel and
the manual checks left to run with `make dev`; questions left open (doc or
spec versus code, contract bugs, changes that would alter `packs/dist/`);
outdated pins; recommendations not applied and why; commits.

**Foreground**: report to the user in the conversation.

**Delegated** (mandatory): when everything is applied, verified and
committed, write the completion file:

```bash
cat > {{DONE_FILE}} <<'END_OF_REPORT'
DONE
<the report>
END_OF_REPORT
```

The first line of the file is `DONE`; the heredoc ends at `END_OF_REPORT`,
so never use that word alone on a line of the report.

Then run `casper notify --message="The full code review is done"`.

If you hit a blocker you cannot resolve on your own (a decision only the
user can make, a broken tool or toolchain), still write that file, with
`BLOCKED` on its first line followed by the reason, run
`casper notify --message="The full review needs your answer"` and
`casper status set blocked`, and ask your question in this session. Once
answered, carry on and overwrite the same file with the final `DONE`
report. Another session waits on that file: never end without writing it.
